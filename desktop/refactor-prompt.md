<ui_rules>
1. 先解决信息架构、视觉层级、布局和交互问题，再处理装饰细节。

2. 一个交互必须只有一种明确行为：
    - 相同操作使用一致的组件、反馈和状态表达。
    - 禁止同一种功能存在多套按钮、弹窗、菜单或表单交互。
    - 禁止让同一个控件在不同页面产生不一致行为。

3. 页面必须具备清晰的主次层级：
    - 每个区域有明确的主要动作。
    - 次要动作不得与主要动作争夺注意力。
    - 禁止无意义地堆叠卡片、边框、容器和分割层。
    - 禁止为了“高级感”滥用渐变、发光、玻璃效果、超大标题或胶囊元素。

4. 间距、字号、圆角、颜色和阴影必须来自现有设计令牌或明确的局部规则。
    - 禁止散落无法解释的任意值。
    - 禁止用大量相近数值模拟设计系统。
    - 嵌套圆角应保持视觉同心关系。
    - 需要几何修正时以视觉对齐为准，而不是机械居中。

5. 每个交互元素必须具备完整且可辨识的状态：
    - 默认、hover、active、focus-visible、disabled。
    - 存在异步操作时，应具备明确的 loading、success 和 error 反馈。
    - 状态变化不得只依赖颜色表达。
    - 禁止点击后没有即时反馈。

6. 可点击元素的有效命中区域至少为 40×40px；相邻控件的命中区域不得重叠。

7. 优先使用语义化 HTML：
    - 操作使用 button。
    - 页面跳转使用链接。
    - 表单控件必须具备可访问名称。
    - 不得用 div 模拟已有原生语义的交互元素。
    - 只有原生语义不足时才使用 ARIA，不得添加错误或冗余的 ARIA。

8. 所有核心交互必须支持键盘操作，并具有清晰、连续、不会被遮挡的 focus-visible 状态。

9. 动效只用于解释状态变化、空间关系或操作结果：
    - 交互状态优先使用可中断的 CSS transition。
    - 禁止使用 transition-all；只过渡实际发生变化的属性。
    - 退出动效应弱于进入动效。
    - 不得用动画掩盖响应迟缓。
    - 必须尊重 prefers-reduced-motion。
    - 不得仅为动效新增依赖；优先复用项目已有方案。

10. 动态变化的数字在确实会造成宽度抖动时使用 tabular-nums。

11. 标题和短文本应避免难看的孤行；长正文、代码和预格式化内容不得强制平衡换行。

12. 界面必须保持布局稳定：
- 加载、内容替换和图片加载不得造成明显跳动。
- 弹窗、菜单和浮层不得溢出视口。
- 文本缩放、长文本和窄屏不得破坏关键操作。
  </ui_rules>

<typescript_react_rules>
1. TypeScript 必须保持严格类型：
    - 禁止新增 any。
    - 禁止用类型断言掩盖不正确的数据结构。
    - UI 状态存在互斥分支时，优先使用判别联合类型。
    - Props 必须表达真实约束，不得使用弱类型对象或魔法 map。

2. React 组件按视觉职责和交互职责划分：
    - 不得把整个页面塞进一个巨型组件。
    - 不得把简单界面碎片化成大量无复用价值的小组件。
    - 通用交互模式应收敛到权威基础组件。
    - 一次性布局不得为了形式强行抽象。

3. 状态必须拥有明确且唯一的来源：
    - 能从 props 或现有状态推导的值不得重复存入 state。
    - 状态应放在能够完整控制该交互的最近公共所有者。
    - 禁止使用 useEffect 同步本可直接推导的状态。
    - 禁止组件、URL 和外部 store 同时保存同一事实而没有明确主从关系。

4. 组件 API 必须清晰：
    - 避免不断增加含义交叉的 boolean props。
    - 复杂视觉变体使用明确的 variant、size 和状态模型。
    - 受控与非受控模式必须明确，不得在运行中隐式切换。
    - 一个能力只能有一个权威组件入口。

5. 优先使用组合而不是复制组件或添加条件分支。禁止建立没有真实使用场景的通用组件系统。

6. 列表必须使用稳定且具有业务意义的 key，不得使用数组索引掩盖身份问题。

7. 注释只解释非显然的交互约束、焦点行为、布局陷阱或可访问性原因。禁止复述 JSX、类型和 Tailwind 类名。
   </typescript_react_rules>

<tailwind_rules>
1. 优先使用项目现有 Tailwind 主题、CSS 变量、语义令牌和基础组件。

2. 禁止通过字符串拼接生成 Tailwind 类名。动态样式必须使用完整类名映射，确保构建工具能够静态识别。

3. 不得为了少量样式添加新的 class 组合库或 variant 依赖。项目已经使用相关工具时应复用现有工具。

4. 禁止无依据地堆积 arbitrary values。只有设计令牌无法表达、且数值来自真实布局计算时才允许使用，并在迭代记录中说明原因。

5. 响应式样式采用移动端优先：
    - 基础类表示最窄布局。
    - 再通过断点逐步增强。
    - 不得只修复桌面端截图而破坏窄屏。

6. 不得使用内联 style 替代静态 Tailwind 样式。只有数值必须在运行时计算时才允许使用内联样式或 CSS 变量。

7. 不得使用 transition-all。根据实际变化属性使用 transition-colors、transition-opacity、transition-transform 或明确的 transition-[...]。

8. 重复且稳定的样式模式应收敛到组件或已有 variant；一次性样式不得为了减少 className 长度而创建无意义抽象。
   </tailwind_rules>

<iteration_workflow>
持续执行以下迭代，不要在每轮之间等待用户确认：

1. UI 审计
    - 读取适用的 AGENTS.md 和现有迭代记录。
    - 检查设计系统、基础组件、Tailwind 配置和目标页面。
    - 在真实浏览器中观察当前界面和操作流程。
    - 通过代码、截图和实际交互收集证据。
    - 优先处理影响理解、操作、反馈、一致性和可访问性的问题。

2. 记录计划
    - 在本轮的工作说明里记录待办、问题证据、影响页面、根因和验收标准,不落盘成长期日志。
    - 每项任务使用待处理、进行中、已完成或阻塞状态。
    - 轮次结束后,提交信息与测试是权威进度记录;git 历史承担考古,文档只描述当前态。

3. 实施
    - 完成本轮选定的所有关联 UI 和交互修改。
    - 同时更新受影响的复用组件、调用方和前端测试。
    - 删除被替代的样式、组件变体和交互入口。
    - 不要在每个小改动后反复运行测试；先完成同一批次修改，再统一验证。

4. 集中验证
   在本轮全部修改完成后统一执行：
    - 格式化。
    - TypeScript 类型检查。
    - lint。
    - 前端构建。
    - 现有组件测试和交互测试。
    - 使用真实浏览器检查本轮修改的页面和操作路径。

   对实质性视觉修改，在相同视口和相同数据状态下保留修改前后截图，以便复核。

   记录执行命令、浏览器视口、测试结果、截图位置和失败证据。不得只写“测试通过”。

   如果验证失败，将失败项纳入本轮继续修复；完成修复后统一重跑受影响的验证。禁止通过跳过测试、降低断言或隐藏错误完成验证。

5. 资源回收
   每轮结束前回收本轮创建或启动的资源，包括：
    - 前端开发服务器和预览服务器。
    - 浏览器自动化或 agent-browser 会话。
    - 临时截图、临时数据、临时目录和占用端口。
    - 本轮专用且不再需要的构建或测试缓存。

   不得删除需要保留的验证证据、用户数据、共享缓存或全局依赖。

6. 轮次收尾
   在提交信息中记录：
    - 审计范围与证据。
    - 已完成和未完成事项。
    - breaking changes 和已更新的调用方。
    - 验证命令、浏览器检查结果和截图。

   把本轮确立的规则写进对应文档的当前态描述;差异本身留在 git 里,不再誊抄一份。
    - 已回收资源。
    - 剩余问题和下一轮审计方向。

   完成记录后立即开始下一轮 UI 审计。
   </iteration_workflow>

不得为了继续迭代而制造视觉变化、组件抽象、动效或 corner case。
</stopping_conditions>
